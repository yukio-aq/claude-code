# 根拠に基づくドキュメント作成

設計判断を扱うドキュメントは、**書いてあることが正しいか**と**読み手に届くか**の 2 つで価値が決まる。本スキルはその 2 つを担保する規律を定める。

---

## 1. 裏取りの規律

### 渡された資料の主張を、そのまま前提にしない

引き継ぎ資料・たたき台・議事録は、**書かれた時点の理解**である。一次資料と突き合わせるまでは仮説として扱う。

### 出典の強さ

| 強さ | 出典 | 扱い |
|---|---|---|
| 最強 | **実装コード・設定ファイル** | 動いている事実。ただし「存在する」ことの証拠であり「正しい」ことの証拠ではない |
| 強 | **ADR・確定仕様・権限定義** | 決定の記録。ただし後続 ADR で修正・失効していないか確認する |
| 中 | **議事録** | 発言の記録。決定なのか検討中なのかを読み分ける |
| 弱 | **引き継ぎメモ・たたき台** | 書き手の理解。必ず上位の出典で裏を取る |
| 証拠なし | 推測・慣習・「たぶんこうだろう」 | **そう書く。** 断定しない |

### やること

- **主張ごとに出典を持つ。** 文書に出典を書かない場合でも、書き手は言えるようにしておく
- **確認できなかったことは、確認できなかったと書く。** 空欄や断定で埋めない
- **参照先が更新されて前提が失効していないか確認する。** リポジトリなら最新に追従してから読む
- **裏取りの対象が広いときは調査を委譲する。** 大量のファイルを読む必要がある場合は `Explore` や `general-purpose` に投げ、結論だけ受け取る。読み込んだ内容を全部メインの文脈に持ち込まない

### アンチパターン

```
✕ 引き継ぎ資料に「○○は既に定義されている」とあったので、そう書いた
  → 一次資料を見たら定義されていなかった。論点の優先順位が丸ごと変わる

✕ 設計書の前提が、参照先の ADR 更新で静かに失効していた
  → 「当時は正しかった」記述は、更新履歴を追わないと誤りと見分けられない

✕ 実装に同じ名前のフィールドがあったので、それを使う前提で書いた
  → 名前が同じでも意味が違った（文書から抽出した自由記述 vs マスタ由来のID）。
     値の生成元まで確認する

✕ 「おそらく〜という想定と思われる」と書いてぼかした
  → 読み手は断定と区別できない。「未確認」と明記して確認先を書く
```

## 2. 読み手とズームレベルを先に決める

### C4 のレベルを粒度の枠組みとして使う

C4 モデルは本来アーキテクチャ**図**のモデルだが、その核心である「**抽象度を混ぜない／読み手に応じてズームレベルを選ぶ**」という規律は、文書全体の粒度設計にも使える。

| レベル | 読み手 | 含めるもの | 含めないもの |
|---|---|---|---|
| **L1 Context** | 経営層・非技術者・他部門 | 何を解決するか。誰と何をやり取りするか。判断してほしいこと | 実装方式・技術用語・内部構造 |
| **L2 Container** | 技術リーダー・インフラ・他チーム | 構成要素とその責務。方式の選択と理由。境界と前提 | クラス設計・関数名・コードの詳細 |
| **L3 Component** | 実装担当者・引き継ぎ先 | 内部構造・データ定義・境界条件・実装上の注意 | 経緯の詳細（別文書へ逃がす） |

**1 つの文書に複数レベルを混ぜない。** 混ざった文書は、どちらの読み手にも長すぎて浅い。

### 図を描くときは C4 の記法に従う

文章の粒度設計に使うのは「ズームレベルの考え方」だけである。**図そのものを C4 として描く場合は、記法（要素の種類・関係の向き・凡例）を守る。** 独自記法と混ぜない。

### 書き始める前に確定させる

```
① この文書は誰が読むか
② その読み手はどのレベルを必要とするか
③ 読み手が読んだあと何をするか（判断する／実装する／承認する／共有する）
```

③が曖昧なまま書くと、情報は正しいのに使えない文書になる。

## 3. 判断を可能にする

### 定性的な問いを、判断基準に変換する

確認依頼・未決事項は、**相手が答えられる形**にして初めて機能する。

```
✕ 「機密性要件を満たせるか」
   → 何をもって満たすのかが示されていない。相手は判断できない

○ 「暗号化キーを事業所ごとに分ける必要があるか。
    分けるなら案B（ただし KB が約20個必要）、分けないなら案A」
   → 実証済みの構成に紐づけたので、構成単位で答えられる
```

変換の手順は、**選択肢を具体化し、それぞれを選んだ場合に何が起きるかを示すこと。** 選択肢が出せないなら、まだ問える段階にない。

### 未決事項に必ず添える 3 点

| 項目 | 理由 |
|---|---|
| **決める人／確認先** | 誰に投げればよいか分からない未決事項は放置される |
| **決まると何が進むか** | 優先順位が判断できる |
| **影響範囲** | 覆ったときの手戻りが読める。「ここが変わっても他は変わらない」と書けると、待たずに進められる |

### 未決のまま進めてよいかを判定する

「確認待ち」を理由に止めてよいのは、**どちらに転んでも作業が無駄になる場合だけ**である。

- 仕組み自体が確定済み要件のために必要なら、採否の確認を待たずに設計できる
- 影響範囲が 1 節に閉じるなら、暫定で書いて注記を添える方が速い

**止める判断をしたときは、何を待っているかを文書に明記する。**

## 4. 却下した案と理由を残す

採用案だけを書いた文書は、**後続の担当者が同じ検討を繰り返す。**

```markdown
| 案 | 内容 | 評価 |
|---|---|---|
| 案A | ... | 採用。理由 |
| 案B | ... | 却下。○○のため |
| 案C | ... | 却下。○○のため |
```

- **却下理由は「劣っているから」ではなく「何と引き換えに何を失うか」で書く**
- 当時の制約を書く。制約が変われば判断も変わるため、将来の読み手が再検討できる
- **前提が変わって選択肢が復活した場合は、その経緯ごと書く**（「当時はコスト面で却下したが、基盤の変更によりその理由は失効した」）

詳細は `rules/accountability.md` に従う。

## 5. 出力形式の選び分け

同じ内容でも、読み手と用途で形式を変える。

| 形式 | 用途 | 粒度 | 注意 |
|---|---|---|---|
| **Markdown（詳細）** | 引き継ぎ・詳細設計のインプット | L3 | 節番号の相互参照を使う。編集を重ねたら参照ずれを点検する |
| **スライド（HTML→PDF）** | 対面説明・合意形成・相談 | L1〜L2 | 1 スライド 1 論点。図を使う。相談したい件は冒頭で予告する |
| **チャット文面** | 確認依頼・非同期の相談 | L1 | 表を使わない（崩れる）。経緯 → 選択肢 → 回答形式の順。10〜20 行に収める |

### 書き分けの原則

- **詳細版を要約してスライドを作る**のであって、スライドを膨らませて詳細版にしない
- **チャット文面では、問いの形が変わった経緯を省かない。** 元資料を読んでいる相手には、理由が分からないと「論点がすり替わった」と受け取られる
- スライドは `slide-deck` 相当のテンプレートがあればそれに従う。なければ印刷用 CSS（`@page size: A4 landscape` / `page-break-after`）を含めて作り、Chrome の `--headless --print-to-pdf` で PDF 化する

## 6. 書いたあとの自己点検

| 観点 | チェック |
|---|---|
| **スコープ** | 依頼された範囲を超えて決めていないか。超えた判断は「暫定」と明示し、合意が必要な事項として立てる |
| **出典** | 断定している箇所に裏はあるか。未確認を断定していないか |
| **読み手** | 想定読み手に不要な粒度が混ざっていないか。用語は読み手に通じるか |
| **参照整合** | 節番号・ファイル名・リンクが実在先を指しているか。編集を重ねた文書は特に |
| **未決の可視性** | 未決事項が 1 箇所に集約され、確認先と影響範囲が書かれているか |
| **判断の再現性** | 却下案と理由が残っているか。半年後の読み手が経緯を追えるか |

### スコープ点検は完成後に行う

作っている最中は逸脱に気づきにくい。**書き上げてから「これは自分が決めてよい範囲だったか」を見直す。** 逸脱していた場合は、削除するのではなく「暫定で方針を置いた。合意が必要」という形に格上げする。

## 7. 進め方

### 対話しながら 1 ステップずつ確定させる

**完成した文書を一度に提示しない。** 読み手が判断すべき点は、文書に書く前に確認する。

```
① これから何を決めるかを示す
② 具体案を提示する（表・図・モックなど、形のあるもの）
③ 確認する
④ 決まったことを文書に落とす
```

### 技術選択そのものを問わない

相手が技術に明るくない場合、**選択を左右する業務上の問いに翻訳して確認する。**

```
✕ 「RLS を使いますか、アプリ層のフィルタだけにしますか」
○ 「応援期間が終わったあと、その人が作った文書は見られなくなるべきですか」
```

業務ルールが決まれば技術選択は従属する。逆は成り立たない。
