## 1. Agile 要件定義

### ユーザーストーリー

**基本フォーマット（INVEST 原則）**

```
As a [ユーザータイプ],
I want [達成したいこと],
So that [得られる価値・理由].
```

**INVEST チェックリスト**

| 項目 | 意味 |
|---|---|
| **I**ndependent | 他ストーリーから独立して完了できる |
| **N**egotiable | スコープを交渉できる（実装方法は固定しない） |
| **V**aluable | ユーザーに具体的な価値を届ける |
| **E**stimable | チームが規模感を見積もれる |
| **S**mall | 1スプリント内で完了できるサイズ |
| **T**estable | 合否を客観的に判定できる |

**アンチパターン**

```
// ❌ 技術実装を指定している
As a developer, I want to add a Redis cache
so that latency is reduced.

// ❌ 受益者が不明確
I want to see order history.  // ← 誰が？

// ❌ 「より良い」「より速い」など計測不能な表現
As a user, I want the app to work better.

// ✅ 正しい例
As a returning customer,
I want to view my past 12 months of orders in a single list,
So that I can reorder items without searching again.
```

### 受け入れ基準（Acceptance Criteria）

**Given/When/Then フォーマット（シナリオベース）**

```gherkin
Scenario: パスワードリセットメールの送信

  Given ユーザーがアカウントに登録済みのメールアドレスを持っている
  When  パスワードリセットフォームでそのアドレスを入力して送信する
  Then  1分以内にリセット用メールが届く
  And   リセットリンクは30分後に失効する
  And   新しいパスワードはセキュリティ要件（8文字以上・英数混在）を満たす必要がある
```

**ルールベース（箇条書き）フォーマット**

```markdown
## ログイン機能 受け入れ基準

- メールアドレスとパスワードが一致する場合、ダッシュボードへリダイレクトする
- 認証失敗時は「メールアドレスまたはパスワードが違います」と表示する（列挙攻撃対策）
- 5回連続失敗でアカウントを15分ロックする
- ロック中は残り時間をエラーメッセージに表示する
```

**受け入れ基準 vs Definition of Done**

| | 受け入れ基準（AC） | Definition of Done（DoD） |
|---|---|---|
| **スコープ** | 個別ストーリーに固有 | チーム全体に共通 |
| **作成タイミング** | バックログリファインメント時 | プロジェクト開始前に一度設定 |
| **内容** | 機能的な完了条件 | コードレビュー済み・テスト通過・デプロイ完了 など |
| **変更** | ストーリーごとに異なる | スプリントレトロで定期見直し |

**DoD テンプレート例**

```markdown
## Definition of Done（チーム共通）

- [ ] コードレビューが少なくとも1名から承認されている
- [ ] ユニットテストが追加されており、全テストがパスしている
- [ ] カバレッジが規定値（ビジネスロジック 95%）を下回っていない
- [ ] staging 環境にデプロイ済みで動作確認できる
- [ ] APIの場合、Swaggerドキュメントが更新されている
- [ ] セキュリティルールのチェックリストを通過している
```

### インセプションデッキ（10の問い）

プロジェクト開始時に全員の共通認識を作るドキュメント。

```markdown
## インセプションデッキ: [プロジェクト名]

### 1. なぜここにいるのか？（Why are we here?）
このプロジェクトが存在する理由・ビジネス背景。

### 2. エレベーターピッチ
[製品名] は [ターゲットユーザー] 向けの [カテゴリ] です。
[主要な価値提案] を提供します。
[競合] とは異なり、[差別化ポイント] があります。

### 3. やらないことリスト（Not List）
IN（やること）                OUT（やらないこと）
----------------------        ----------------------
- iOS/Androidアプリ           - デスクトップアプリ
- 日本語対応                  - 多言語対応（v1では）
- クレカ決済                  - 後払い・銀行振込

### 4. 夜も眠れなくなること（What keeps us up at night?）
リスクと不確実性のリスト。

### 5. ご近所さんを紹介する（Meet the neighbors）
外部依存システム・チームの一覧。

### 6. 解決策を絵に描く（Show the solution）
アーキテクチャ概要図。

### 7. 何がどれだけ必要か？（What's going to take?）
チーム構成・スキルセット。

### 8. 期間を見せる（Show the schedule）
マイルストーンと大まかなタイムライン。

### 9. 何を諦めるか？（What's it going to take?）
スコープ・品質・時間・コストのトレードオフ。

### 10. 大事なことは何か？（What does it take to win?）
成功の定義・KPI。
```

### ストーリーマッピング

ユーザーの行動フロー全体を可視化し、MVP のスコープを決める技法。

```
水平軸: ユーザーのアクティビティ（左→右 = 時系列）
垂直軸: 優先度（上 = 最重要）

[ 商品検索 ] ─── [ カートに追加 ] ─── [ 決済 ] ─── [ 注文確認 ]
     │                  │                 │              │
  フリーワード        数量変更           クレカ         メール通知    ← MVP（v1）
  検索                カート削除         コンビニ払い   SMS通知       ← v2
  カテゴリ絞り         保存リスト         後払い         返品フロー     ← v3
```

**アンチパターン**

- アクティビティではなく機能（フィーチャー）から始める
- ユーザーが1人しか想定されていない（ペルソナを複数検討する）
- マップを静的なドキュメントとして扱う（定期的に更新する）
- 強い声の持ち主だけが発言する（ファシリテーターが発言権を均等に配分する）

### MoSCoW 優先度付け

| 分類 | 基準 | 目安 |
|---|---|---|
| **Must have** | なければリリースできない | 全体の ~60% |
| **Should have** | 重要だが代替手段がある | ~20% |
| **Could have** | あれば良いが影響は小さい | ~20% |
| **Won't have** | 今回のスコープ外（将来的に検討） | — |

```markdown
## v1.0 MoSCoW

### Must have
- [ ] メールアドレス＋パスワードでの認証
- [ ] 商品一覧・詳細ページ
- [ ] カート機能
- [ ] クレカ決済（Stripe）

### Should have
- [ ] 注文履歴
- [ ] プロフィール編集

### Could have
- [ ] ウィッシュリスト
- [ ] 商品レビュー

### Won't have（v1では対象外）
- SNSログイン
- ギフトラッピング
```

### 要件記述の SMART 基準

```markdown
要件ID: AUTH-001
要件名: ログインレスポンスタイム

❌ 悪い例:
「ログインは速く応答すること」

✅ 良い例（SMART）:
「通常負荷（同時接続100ユーザー以下）において、
 ログインAPIは認証成功・失敗いずれの場合も
 p95 で 300ms 以内にレスポンスを返すこと。
 負荷テスト環境: AWS t3.medium 2台構成」

S - Specific（具体的）: ログインAPIに限定
M - Measurable（計測可能）: p95 300ms
A - Achievable（達成可能）: 実現可能な数値
R - Relevant（関連性）: ユーザー体験に直結
T - Time-bound（期限）: 負荷テストで初回リリース前に確認
```

### ユースケース記述

```markdown
## UC-003: 商品をカートに追加する

| 項目 | 内容 |
|---|---|
| アクター | 会員ユーザー |
| 事前条件 | ユーザーがログイン済み、商品詳細ページを表示中 |
| 事後条件（成功） | カートに商品が追加され、カートアイコンの数が更新される |
| 事後条件（失敗） | カートは変更されない |

### 基本フロー
1. ユーザーが「カートに追加」ボタンをクリックする
2. システムが在庫数を確認する
3. システムがカートに商品と数量を記録する
4. システムがカートアイコンの数を更新する
5. システムが「追加しました」のトースト通知を表示する

### 代替フロー
2a. 在庫不足の場合:
  - システムが「在庫不足」のエラーを表示する
  - ユースケース終了

### 例外フロー
3a. セッションが切れている場合:
  - システムがログインページにリダイレクトする
  - ログイン後、カート追加を再実行する
```

### トレーサビリティマトリクス（RTM）

要件 → 設計 → 実装 → テストを双方向に追跡する。

```markdown
| 要件ID | 要件概要 | 設計書セクション | 実装ファイル | テストケースID |
|---|---|---|---|---|
| AUTH-001 | ログインp95 300ms | arch/auth.md#perf | src/auth/login.ts | TC-AUTH-P-001 |
| AUTH-002 | 5回失敗でロック | arch/auth.md#lockout | src/auth/lockout.ts | TC-AUTH-F-001 |
| CART-001 | 在庫確認 | arch/cart.md#stock | src/cart/add.ts | TC-CART-001 |
```

**RTM の3種類**

- **前向きトレーサビリティ**: 要件 → テストケース（カバレッジ確認）
- **後ろ向きトレーサビリティ**: テストケース → 要件（余分なテストの発見）
- **双方向トレーサビリティ**: 変更影響範囲の分析に使用

## 3. AI・エージェントシステム固有の要件（2025-2026年版）

### LLM アプリの品質要件

```markdown
## LLM品質要件定義テンプレート

### 精度・品質要件
| 指標 | 定義 | 目標値 | 測定方法 |
|---|---|---|---|
| 回答精度（Accuracy） | ゴールデンセットに対する正解率 | ≥ 85% | LLM-as-Judge + 人手評価 |
| ハルシネーション率 | 事実に反する内容を含む回答の割合 | ≤ 5% | Lynx / Galileo 等で自動検出 |
| 根拠付き回答率（Groundedness） | RAGソースに基づいた回答の割合 | ≥ 90% | Faithfulness スコア |
| 関連性（Relevance） | ユーザーの質問に対する回答の適合度 | ≥ 4.0/5.0 | 自動スコアリング |
| 毒性（Toxicity） | 有害・攻撃的な表現を含む回答の割合 | ≤ 0.1% | 自動フィルタリング |

### レイテンシ要件
| シナリオ | p50 | p95 | p99 |
|---|---|---|---|
| 短文応答（チャット） | 500ms | 1,500ms | 3,000ms |
| 長文生成（レポート） | 3s | 10s | 20s |
| エージェント（多段推論） | 5s | 30s | 60s |

※ストリーミングレスポンスで Time-to-First-Token (TTFT) を別途計測すること
```

### AIエージェントの安全要件

Human-in-the-Loop（HITL）設計のリスクレベル分類：

```markdown
## エージェント安全要件

### リスクレベル分類とアクション制限

| リスクレベル | 例 | 承認要否 | タイムアウト |
|---|---|---|---|
| **LOW** | 情報検索・要約・ドラフト生成 | 不要（自動実行） | — |
| **MEDIUM** | メール下書き・カレンダー仮予約 | 任意確認（15秒以内） | タイムアウト→キャンセル |
| **HIGH** | メール送信・DB更新・PIIアクセス | 人間の明示的承認（2分以内） | タイムアウト→フェイルセーフ |
| **CRITICAL** | 金融決済・本番DB削除・権限変更 | 二者承認必須（15分以内） | タイムアウト→エスカレーション |

### フォールバック要件
- エージェントが3回連続で目標達成に失敗した場合、人間にエスカレーションする
- 外部APIエラー時は指数バックオフで最大3回リトライし、失敗したら graceful degradation
- 不確実性が閾値（confidence < 0.7）を下回る出力は必ずフラグを立てる
- 緊急停止（KILLSWITCH）: エージェントが意図しない副作用を起こした場合の即時停止手順

### 承認チェックリスト（高リスク操作）
1. [ ] 意図（Intent）の確認
2. [ ] データの出所（Data Lineage）の確認
3. [ ] 権限スコープ（Permissions Chain）の確認
4. [ ] 影響範囲（Blast Radius）の確認
5. [ ] ロールバック手順の確認

### 監査要件
- 全ツール呼び出しのログ（入力・出力・タイムスタンプ・実行者）を保存
- 保存期間: 最低90日（コンプライアンス要件に応じて延長）
- EU AI Act（2026年8月施行）対応: 高リスクAIは人間監視・介入機能が必須
```

### コスト要件

```markdown
## LLMコスト要件

### トークン消費上限（per request）
| 機能 | Input上限 | Output上限 | モデル推奨 |
|---|---|---|---|
| チャット応答 | 4,000 tokens | 1,000 tokens | Sonnet / Flash |
| ドキュメント要約 | 32,000 tokens | 2,000 tokens | Sonnet |
| 複雑な推論・設計 | 8,000 tokens | 4,000 tokens | Opus（必要時のみ） |
| バッチ分類処理 | 2,000 tokens | 500 tokens | Haiku / Mini |

### 月次コスト上限
| 環境 | 上限 | アラート閾値 |
|---|---|---|
| 開発 | $100/月 | $80（80%） |
| ステージング | $500/月 | $400（80%） |
| 本番 | $5,000/月 | $4,000（80%） |

### コスト最適化要件
- キャッシュ可能なLLM呼び出しは積極的にキャッシュすること（同一プロンプトの20-40%は冗長）
- タスクに必要な最小モデルを選択すること（Opus > Sonnet > Haiku の順でコスト大）
- プロンプトの長さを監視し、不要なコンテキストを除去すること
- バッチ処理可能なタスクはリアルタイムAPI呼び出しを避けること

### レート制限要件
- 1ユーザーあたり: 10 requests/分（spike protection）
- 全体: 1,000 requests/分（プロバイダーのrate limit余裕を持たせる）
- 超過時: 429 Too Many Requests + Retry-After ヘッダ
```

### アラート設定
| 条件 | 閾値 | アクション |
|---|---|---|
| ハルシネーション率急増 | > 10%（1時間） | PagerDuty 通知 |
| レイテンシ劣化 | p95 > 5s（5分間） | Slack アラート |

| エラー率 | > 5%（10分間） | オンコール起動 |

1. トークン消費量（モデル・機能・ユーザー別）
2. レイテンシ分布（p50 / p95 / p99）
3. 品質スコアの推移（日次）
4. コスト推移と月次予算消化率
5. エラー率・リトライ率
```

## 4. 非機能要件フレームワーク

### FURPS+

Hewlett-Packard が開発した要件分類モデル。

```markdown
## FURPS+ チェックシート

### F - Functionality（機能性）
セキュリティ・監査・認可など、ユースケースに現れにくい横断的機能要件

例:
- すべてのAPIエンドポイントは認証を要求する
- 管理操作はすべて監査ログに記録する

### U - Usability（使いやすさ）
学習容易性・操作性・アクセシビリティ

例:
- 初めてのユーザーがチュートリアルなしで主要機能を5分以内に操作できる
- WCAG 2.1 AA 準拠

### R - Reliability（信頼性）
可用性・障害許容性・回復性

例:
- 月次稼働率 99.9%（ダウンタイム ≤ 43.8分/月）
- 障害発生時、最大データ損失 = 直近1時間分（RPO: 1h）
- 障害から2時間以内に復旧（RTO: 2h）

### P - Performance（パフォーマンス）
応答速度・スループット・スケーラビリティ

例:
- APIレスポンス p95 ≤ 500ms（通常負荷）
- 同時接続1,000ユーザーまでスケールできる

### S - Supportability（サポート性）
保守性・テスト容易性・設定容易性

例:
- 新機能を既存コードを変更せずに追加できる（OCP）
- ユニットテストカバレッジ 95% 以上
- 環境変数で全外部サービスURLを設定できる

### + 追加カテゴリ
- **Design constraints**: 使用技術スタック・アーキテクチャの制約
- **Implementation**: 言語・標準・ツールの制約
- **Interface**: 外部システム・APIの制約
- **Physical**: ハードウェア・デプロイ先の制約
```

### ISO/IEC 25010:2023（SQuaRE）製品品質モデル

2023年に2011年版から改訂。**8特性 → 9特性** に拡張。

```markdown
## ISO/IEC 25010:2023 プロダクト品質特性

| 特性 | 2023年版の変更点 | 主なサブ特性 |
|---|---|---|
| **Functional Suitability** | 変更なし | 完全性・正確性・適切性 |
| **Performance Efficiency** | 変更なし | 時間効率・資源効率・容量 |
| **Compatibility** | 変更なし | 共存性・相互運用性 |
| **Interaction Capability** | ※旧: Usability | 適切さ・学習容易性・操作性・**包括性（新）**・UI美観 |
| **Reliability** | maturity → faultlessness に改名 | 成熟性・可用性・耐障害性・回復性 |
| **Security** | **resistance（新）** サブ特性追加 | 機密性・完全性・否認防止・説明責任・真正性 |
| **Maintainability** | 変更なし | モジュール性・再利用性・分析容易性・変更容易性・テスト容易性 |
| **Flexibility** | ※旧: Portability / **scalability（新）** | 適応性・**スケーラビリティ（新）**・設置容易性・置換容易性 |
| **Safety** | **2023年版で新規追加** | 操作制約・リスク識別・フェイルセーフ・ハザード警告・安全統合 |

### 2023年版の主な変更ポイント
1. **Safety が独立した特性として追加** → 医療・自動車・AIシステムへの対応
2. Usability → **Interaction Capability** に改名（スコープ拡大）
3. Portability → **Flexibility** に改名（スケーラビリティを含むよう拡張）
4. AI品質拡張（ISO/IEC 25059）: 透明性・公平性・説明可能性 が検討中

### AI システムへの適用拡張（ISO/IEC 25059 ドラフト）
```markdown

Functional Suitability:
  + functional adaptability（学習データの変化への適応）

Reliability:
  + robustness（想定外入力への耐性）

Security:
  + resistance（プロンプトインジェクション等への耐性）

Interaction Capability:
  + user controllability（ユーザーがAIの動作を制御できる）
  + transparency（AI の動作根拠の説明可能性）

## 5. よくある落とし穴・アンチパターン（全般）

### 要件定義全般

```markdown
## アンチパターン集

### 1. 曖昧要件のまま進む（最多発）
❌ 「パフォーマンスを改善すること」
✅ 「APIのp95レスポンスタイムを現状の1,200msから500ms以下に改善すること」

### 2. 解決策を要件として書く
❌ 「Redisキャッシュを実装すること」
✅ 「商品一覧ページの初回表示後、10分以内の再アクセスでは
    サーバーリクエストなしに表示すること」

### 3. 非機能要件を後回しにする
アーキテクチャが決まってから性能要件が来ると手遅れになる。
→ 設計開始前に FURPS+ / ISO 25010 で網羅的にリストアップする

### 4. AIシステムで「精度99%」を要件にする
LLMの確率的な性質を無視した非現実的要件。
→ タスク種別ごとに測定可能な指標と閾値を設定する（上記の品質要件テンプレート参照）

### 5. 人間介入の設計を後付けにする
エージェント自動化を先に作り、後からガバナンスを追加しようとすると構造改修が必要になる。
→ リスクレベル分類とHITL設計は要件定義フェーズで確定する

### 6. コスト要件を定義しない
本番投入後にLLMコストが想定の10倍になるケースが頻発（2025年時点）。
→ トークン上限・月次予算・アラート閾値を要件として明示する

### 7. ストーリーが大きすぎる（Epic化）
1スプリントで完了できないストーリーはスプリント計画を破綻させる。
→ INVEST の「S（Small）」を満たすまでストーリーを分割する
```

## 6. 2025-2026年の新しい傾向

```markdown
## 最新トレンド（2026年時点）

### 1. AI支援による要件管理（LLM4RE）
- 2024年から急成長: LLM for Requirements Engineering の論文数が前年比136%増
- 実用化されているユースケース:
  - ユーザーインタビューから自動的にユーザーストーリーを生成
  - 既存の要件からテストケースを自動生成
  - 要件の曖昧さ・矛盾を自動検出
  - 多言語チームへの要件翻訳・意図保持
- 注意: AIが生成した要件はレビュー必須（幻覚リスク）

### 2. AIエージェント固有の要件カテゴリの確立
- THROTTLE / ESCALATE / FAILSAFE / KILLSWITCH が標準的な安全仕様項目に
- EU AI Act（2026年8月完全施行）対応: 高リスクAIは要件段階で監査証跡の設計が必要
- Agent Behavioral Contracts（エージェント行動仕様）が形式化されつつある

### 3. オブザーバビリティファースト設計
- LLMシステムでは事後的にオブザーバビリティを追加するのが困難
- 要件定義フェーズでトレーシング・評価パイプライン・アラートを設計する

### 4. ISO/IEC 25010:2023 での Safety 特性新設
- AIシステム・自動車・医療機器向けに Safety が独立特性として追加
- フェイルセーフ・ハザード警告が要件項目として標準化

### 5. Context Engineering の台頭
- LLMアプリの品質はプロンプト設計からコンテキスト設計へシフト
- RAGパイプライン・動的メモリ・ツールインタラクションの設計が要件項目に

### 6. コスト要件の重要性増大
- 2025年の開発者調査でコスト管理がAIチームの最大懸念事項
- 月次予算上限・トークン消費上限・コストアラートが要件の標準項目に
