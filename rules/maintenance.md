# スキルメンテナンス・運用ルール

## 1. 定期見直しのスケジュール（四半期サイクル）

情報の鮮度を保つため、原則として **3ヶ月に一度（1月、4月、7月、10月）** 全体的な見直しセッションを行う。ただし、対象の技術特性に応じて優先度と頻度を調整する。

| 優先度 | 更新スパン | 対象領域 |
| :--- | :--- | :--- |
| **極高 (Critical)** | 1〜2ヶ月 | AI/Agent関連 (`ai-agent-patterns`, `mastra`, `llamaindex` 等) |
| **高 (High)** | 3ヶ月 | Web/Mobileフレームワーク (`vue`, `laravel`, `nextjs`, `ios`, `android`) |
| **中 (Medium)** | 6ヶ月 | 言語仕様、DB、インフラ (`typescript`, `postgresql`, `mysql`, `observability`) |
| **低 (Low)** | 12ヶ月 | 設計思想・アーキテクチャ (`ddd`, `clean-architecture`, `system-design`) |

## 2. トークン・時間効率のための実行ルール

一度に大量のファイルを更新すると、トークン上限への到達や推論精度の低下を招くため、以下の制約を守る。

- **バッチ更新の制限:** 1つのセッションで更新するスキルファイルは **最大3〜5件** に留める。
- **差分更新の原則:** ファイル全体を書き換えるのではなく、最新のドキュメントと既存スキルの「差分（新機能、非推奨化、Breaking Changes）」のみを調査し、反映する。
- **調査の先行:** 実装エージェントを動かす前に、まず `docs-lookup` または `web_fetch` を使用して「何が変わったか」のサマリーを作成し、ユーザーに提示する。

## 3. 更新トリガー（定期以外）

定期スケジュール以外でも、以下のイベントが発生した場合は随時更新を検討する。

- **メジャーアップデート:** 使用ツールのメジャーバージョンがリリースされたとき。
- **不整合の検知:** `continuous-learning` で抽出された新しいパターンが、既存の `SKILL.md` と矛盾したとき。
- **実装中の違和感:** エージェントが提案するコードが最新のライブラリ仕様でエラーになったとき。

## 4. メンテナンス手順

1.  **スキャン:** `skills/` 配下の全 `SKILL.md` の「情報収集日」を確認する。
2.  **リストアップ:** 更新期限が切れている（または切れそうな）ファイルを、上記の優先度に基づきリストアップする。
3.  **計画提示:** 「今回は〇〇と△△のスキルを最新化します（想定トークン消費：中）」といった形でユーザーに作業範囲を提案する。
4.  **順次実行:** 承認された範囲で、調査・更新・日付の書き換えを実行する。
