# ライブラリ管理と設計遵守ルール

## 1. 設計（Architect / ADR）の遵守

- **原則:** すべての実装は、`architect` または `planner` が事前に定義した設計、および `docs/adr/` に記録された決定事項（ADR）に従わなければならない。
- **逸脱の禁止:** 実装中に設計の不備や改善点に気づいた場合は、勝手に修正せず、必ずユーザーまたは `architect` に報告し、設計の更新を仰ぐこと。
- **優先順位:** プロジェクト固有の設計（ADR） > 一般的なベストプラクティス > エージェントの個人的な好み。

## 2. ライブラリの追加・変更（禁止事項）

- **勝手な追加の禁止:** `package.json`, `composer.json`, `build.gradle`, `requirements.txt` 等へのライブラリ追加を独断で行ってはならない。
- **標準ライブラリの優先:** 言語の標準機能（Standard Library）や、既にプロジェクトに導入済みのライブラリで実現可能な場合は、新しい依存関係を追加しない。
- **軽量・安定性の重視:** 新しいライブラリが必要な場合は、以下の基準で候補を提示し、ユーザーの承認を得ること。
  - **ライセンス:** 商用利用可能か（MIT, Apache 2.0 推奨）。
  - **保守状況:** メンテナンスが継続されているか（最終更新、Issueの消化速度）。
  - **サイズ:** バンドルサイズや依存関係の連鎖が許容範囲内か。

## 3. 依存関係の固定と管理

- **バージョン固定:** ライブラリのバージョンは原則として固定、またはマイナーアップデートまで（`^` や `~`）を適切に使い分ける。
- **ロックファイルの更新:** パッケージマネージャーによる更新時は、ロックファイル（`package-lock.json`, `composer.lock`, `pnpm-lock.yaml` 等）が正しく更新されていることを確認する。
- **未使用依存の排除:** 実装の結果、不要になったライブラリやデッドコードは速やかに削除する。

## 4. プロセスと手順

1. **インプットの確認:** 実装前に必ず既存の `docs/adr/` および直近の `plan.md` を読み込み、技術選定の経緯を理解する。
2. **提案と承認:** 計画にないライブラリが必要になった場合、まず `architect` に相談（エージェント呼び出し）し、メリット・デメリットを整理してユーザーに提案する。
3. **実行:** ユーザーの承認（または `architect` による ADR 更新）が得られた場合のみ、インストールコマンドを実行する。
