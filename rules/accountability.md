# 説明責任ルール

すべての設計・実装・レビューにおいて、判断の根拠を記録する。
「何をしたか」ではなく「なぜそうしたか」が残ることで、人間が意思決定を追跡できる状態を維持する。

---

## 設計フェーズ（architect / planner）

- 技術選定・アーキテクチャ判断は必ず ADR に記録する
- ADR には採用理由だけでなく、**却下した選択肢とその理由**を明記する
- 「当時の制約」「将来の開発者への引き継ぎ」を Consequences セクションに必ず書く

## 実装フェーズ（*-implementer）

- **非自明な実装判断**（複数アプローチがあった・パフォーマンストレードオフがあった・標準でない実装をした）は PR description に理由を記録する
- コードコメントは「なぜ」だけ書く。コードを読めばわかる「何を」は書かない
- 実装後チェックリストに「根拠の記録」を含める

## レビューフェーズ（*-reviewer）

- 指摘事項には必ず **根拠**（参照するルール・原則・リスク）を添える
- 「問題があるから直して」ではなく「〇〇ルール違反のため・〇〇リスクがあるため」の形式で示す
- 根拠のない指摘は出力しない

---

## 出力フォーマット（レビュー指摘の必須フィールド）

```
### [重大度] 問題タイトル
**場所:** path/to/file:line
**問題:** 何が問題か
**根拠:** どのルール・原則・リスクに基づく指摘か（例: rules/security.md / OWASP A03 / N+1問題）
**修正案:** どう直すか
```
