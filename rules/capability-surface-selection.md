# ケイパビリティの配置判断

新しいルール・スキル・フック・MCPを追加するとき、どこに置くかを以下の質問フローで決める。

---

## 判断フロー

```
毎回・確定的・判断不要？
  ↓ Yes → rules/
  ↓ No
判断が必要・重い・タスク依存？
  ↓ Yes → skills/
  ↓ No
ツール呼び出し前後に自動で走らせたい？
  ↓ Yes → hooks/
  ↓ No
ステートフルなセッション・複数クライアントで共用？
  ↓ Yes → MCP サーバー
  ↓ No  → CLI スクリプト / skill から直接 API 呼び出し
```

---

## rules/ に置くもの

- 常時適用される禁止事項・命名規則・コーディング規約
- 判断が不要な安全制約（secrets をコミットしない等）
- エージェントの基本行動指針

**置いてはいけないもの:** 大規模なプレイブック、オプショナルなワークフロー、毎回読み込む必要のない重いコンテキスト

---

## skills/ に置くもの

- ライブラリ・フレームワーク固有の実装パターン
- 複数ステップのワークフロー・判断ガイド
- タスクによってのみ必要になる詳細なドメイン知識

**置いてはいけないもの:** 単純な定数、毎回適用すべき不変条件（rules/ に置く）

---

## hooks/ に置くもの

- PreToolUse: ツール実行前の安全チェック・ガード
- PostToolUse: ファイル保存後のフォーマット・lint
- UserPromptSubmit: セッション開始時の初期化

**置いてはいけないもの:** 重いビジネスロジック、エージェントの判断を必要とする処理

---

## MCP サーバーにするもの

以下の両方を満たす場合のみ:
1. **ステートフル** — セッションをまたいだ状態が必要（ブラウザデバッグセッション等）
2. **普遍的** — ほぼすべてのプロジェクト・ユーザーに適用できる

**典型的なアンチパターン:**
- 1回のAPIコールで完結するもの → skill から直接 API 呼び出し
- `gh` CLI で代替できるもの → `github-ops` skill 相当を作る
- ハーネスのネイティブ機能で吸収済みのもの（memory・web search・extended thinking）→ 不要

---

## 判断に迷ったときの優先順位

```
シンプルさ > 機能性
rules/ > skills/ > hooks/ > MCP
（より狭いスコープが正しい）
```

3つのハーネス向けに同じ内容をコピーすることになったら、共有ソース（skills/）に置いてアダプタ層だけをハーネス固有にする。
